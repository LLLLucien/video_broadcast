# 发送端当前情况（broadcaster）

> **给谁看**：接收端（viewer，yht 负责）开发与联调时参考；也作为 lmq 发送端自己的状态备忘。
> **更新**：2026-09-02（M2 编码到文件、M3 发送到网络均已实测通过）
> **配套**：项目总览见 `docs/lmq的上下文总结.md`；接口契约以 `common/params.h` 与 SRS V0.4(1) 为准。

---

## 1. 一句话现状

发送端已完成：**OpenCV 采集 → BGR 转 YUV420P → libx264 编码 H.264 → FFmpeg rtp muxer 推 UDP/RTP**。
已用两种标准接收端验证可播：**ffplay** 和 **VLC（snap 版）**。阶段一验收点「VLC 当接收端能播 → 发送端正确」达成。

## 3. 命令行用法

```bash
./broadcaster [-s 采集源] [-f 输出] [-t 秒数]

  -s 0        摄像头 /dev/video0（默认）
  -s test     测试画面（无摄像头时验证链路；生成渐变底+移动白块+帧号）
  -s 文件     视频文件作采集源
  -f out.mp4  录制 mp4（M2，默认）
  -f rtp://IP:端口   推 RTP 网络流（M3）
  -t 秒数     运行时长；0 = 持续到按 q
```

实测示例：

```bash
# 摄像头推流到本机（验证用）
./broadcaster -s 0 -f rtp://127.0.0.1:5004 -t 60

# 推流到指定机器（跨机联调时用对方 IP）
./broadcaster -s 0 -f rtp://192.168.1.100:5004 -t 60

# 无摄像头自测
./broadcaster -s test -f rtp://127.0.0.1:5004 -t 10
```

运行时会在**当前工作目录**生成 `broadcast.sdp`（接收端"说明书"），并向控制台每 1 秒打印"已发送 N 帧"。

## 4. 已验证的测试场景（2026-09-02）

| 场景 | 命令 | 结果 |

## 5. 推流技术参数（接收端务必对齐）

| 参数 | 值 | 备注 |
|---|---|---|
| 分辨率 / 帧率 | 640×480 / 30fps | YUV420P |
| 编码 | H.264，libx264 软编（preset=ultrafast） | 无 B 帧 |
| 码率 | 2 Mbps | 契约 1~4Mbps |
| GOP | 60 帧（约 2 秒一个 I 帧） | 断流后 ≤2s 自动恢复 |
| RTP payload | 96 | |
| 采样时钟 | 90000 Hz | |
| 端口 | 5004（UDP，单播） | 阶段三改组播 239.255.0.1:5004 |
| RTP 分包 | FU-A 等，由 FFmpeg rtp muxer 自动完成 | 发送端不手写 socket |

> ⚠️ **SPS/PPS 关键点（联调最容易黑屏的根因）**
> 发送端编码器设了 `AV_CODEC_FLAG_GLOBAL_HEADER`，**RTP 流内不带 SPS/PPS**，SPS/PPS 只写在 SDP 的 `sprop-parameter-sets` 字段。
> - 若接收端用 FFmpeg 打开 `broadcast.sdp`（sdp demuxer）：自动用 sprop 配置解码器，无感，**推荐**。
> - 若接收端自研裸收 RTP：必须自己解析 SDP 的 `sprop-parameter-sets` 并在解码前喂给解码器（或复用 FFmpeg 接口），否则永远等不到解码器参数 → 黑屏。

## 6. 测试中遇到的问题与解决（含 VLC 排查全过程时间线）

> 本节按 2026-09-02 实测时**实际操作的先后顺序**记录，每一步试了什么、看到什么、结论是什么，供接收端参考避坑。

### 6.1 ffplay 收流报错：协议白名单（第 1 个问题，先解决）

- **现象**：`ffplay broadcast.sdp` 报 `[rtp] Protocol 'rtp' not on whitelist 'file,crypto,data'!`，随后 `Invalid data found when processing input`。
- **原因**：Ubuntu 编译的 ffmpeg 出于安全加固，默认协议白名单只有 `file,crypto,data`，**不含 rtp/udp**。
- **解决**：加白名单参数 → `ffplay -protocol_whitelist file,rtp,udp broadcast.sdp` → ✅ **出画面**（证明发送端推流本身正常，问题在收流工具）。

### 6.2 VLC 黑屏：完整排查时间线（重点）

**第 1 步：在 VLC 里填地址收流 → 黑屏**
- 操作：VLC「媒体→打开网络串流」填 `rtp://127.0.0.1:5004`。
- 结论：**此路不通**。裸 RTP H.264 必须靠 SDP 提供 payload 映射和 SPS/PPS 才能初始化解码器，光填地址拿不到。正确做法是**打开 sdp 文件**（`vlc broadcast.sdp` 或 GUI 打开文件）。

**第 2 步：`vlc broadcast.sdp`（系统版 VLC）→ 仍黑屏**
- 系统版 `/usr/bin/vlc` 版本 3.0.20-3build6（Ubuntu 22.04 自带，较老）。
- 抓日志 `cvlc --verbose 2 broadcast.sdp`，关键行：
  ```
  sap demux: unexpected SDP line: 0x62     ← 0x62 即字母 'b'
  sap demux warning: invalid SDP
  ...
  using demux module "ps"                  ← 错误回退到 MPEG-PS 解复用器
  ps demux warning: garbage at input
  ```
- 初步定位：**VLC 3.0.x 内置的 SDP 解析器（sap demux）对 ffmpeg 6.x 生成的 sdp 不兼容**，判无效后乱选 demuxer。

**第 3 步：手工"手术"改 sdp，试图迁就系统版 VLC → 仍然黑屏**
- ① 删 `b=AS:2000` 行（sap demux 就是报在这行 'b' 上）→ 仍黑屏。
- ② 强制 `--demux=rtp` → 直接报 `无法打开 MRL file://...broadcast.sdp`，更糟。
- ③ 重做格式：删 `a=tool:` 行、`s=No Name` 改 `s=Video`、补 `a=rtcp:5005`、去掉 fmtp 行内多余空格——**第一次 sed 把 `a=fmtp:96 ` 必需的空格也删了**，生成 `a=fmtp:96packetization-mode=1`（改过头），修正为只删分号后的空格后得到内容正确的 `vlc.sdp` → 仍黑屏。
- 阶段结论：格式问题只是表层，**系统版 VLC 3.0.20 对这条流的兼容性就是不行**。

**第 4 步：回看发送端代码，找到深层原因**
- 发现编码器设了 `AV_CODEC_FLAG_GLOBAL_HEADER`：SPS/PPS 只在文件头/SDP 里，**RTP 流内不带**。接收端要解码只能靠 SDP 的 `sprop-parameter-sets`。ffplay 正确吃进了 sprop 所以能看；VLC 一旦 SDP 解析环节出错，就拿不到 SPS/PPS，**永远解不出画面**。

**第 5 步：决定升级 VLC → 装完发现还是 3.0.20**
- 执行 `sudo snap install vlc`，装出来是 **3.0.20-1-g2617de71b6**——一度以为白装。原因：**VideoLAN 至今没出 VLC 4.x 稳定版**，snap 稳定频道里也只有 3.0.x（只是比 Ubuntu 系统版新一些的 git 快照）。

**第 6 步：用 snap 版 VLC 打开原始 broadcast.sdp → ✅ 出画面**
- 命令：`/snap/bin/vlc broadcast.sdp`（发送端保持推流）。
- 结论：**VLC 版本差异是决定性变量**——系统版（3.0.20-3build6）SDP 解析有 bug，snap 版（3.0.20-1-g2617de71b6）正常。**本机验证 VLC 一律用 `/snap/bin/vlc`**，原版 `broadcast.sdp` 直接能播，不需要任何手工改造。

**附加现象**：出画面后 VLC 日志有 `main decoder error: buffer deadlock prevented`
- 非致命（启动缓冲/解码器短暂忙时的自救提示），画面流畅可忽略；若卡顿可加 `--network-caching=300 --rtp-caching=200`。

### 6.3 UDP 协议特性补充

- UDP **无连接**：发送端往 `IP:端口` 丢包，接收端 bind 端口即收，没有握手。
- 同机验证收发都用 `127.0.0.1` 即可，不必改虚拟机网卡 IP（192.168.197.129 只在跨机演示时才用）。
- 接收端程序建议 **bind `0.0.0.0:5004`**（不挑发送端 IP，跨机联调不用改接收端代码）。

## 7. 给接收端（yht）的对接建议

1. 先各自同机自测：发送端推 `127.0.0.1:5004`，接收端 bind `0.0.0.0:5004`。
2. 首版接收端建议直接用 FFmpeg 打开发送端生成的 `broadcast.sdp`（`avformat_open_input("broadcast.sdp")`），把解码显示先跑通；再考虑自研 RTP 收包。
3. 联调时以 `common/params.h` 契约为准：PT=96、90000Hz、5004 端口、640×480@30fps、H.264。
4. 发送端每次启动会重新生成 `broadcast.sdp`，接收端需拿**同一次推流**对应的 sdp（参数固定时内容不变）。
5. 抓包验证网络层：`sudo tcpdump -i any -n udp port 5004`。
