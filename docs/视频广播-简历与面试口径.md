# 一、项目一句话定位

基于 **Linux + C++17 + Qt Widgets + OpenCV + FFmpeg** 的局域网**单向视频广播系统**：发送端采集摄像头画面，H.264 编码后经 UDP 组播广播，多台接收端同时收看（电子教室模型）。1 发多收、端到端延迟目标 ≤300ms、断流自动恢复。

原始裸数据 640×480@30fps ≈ 216Mbps，远超带宽与单个 UDP 包上限，因此必须压缩编码（H.264 后约 2Mbps）并经 RTP 拆包传输、接收端按序号重组。

# 三、系统架构与真实数据链路

```
[发送端 Broadcaster]（本人职责，纯 C++ 引擎 + Qt 壳）
摄像头 /dev/video0（失败自动回退测试画面 test）
  → OpenCV VideoCapture 采集 640×480 BGR
  → sws_scale：BGR → YUV420P
  → libx264 软编：H.264（ultrafast / Baseline / 2Mbps / GOP=60 / 无B帧 / GLOBAL_HEADER）
  → FFmpeg rtp muxer：RTP 拆包封装（自动，含 FU-A）
  → UDP 组播发送 239.255.0.1:5004（payload type 96 / 90000Hz）
  → 首关键帧后 av_sdp_create 生成 broadcast.sdp
  → 按 30fps 真实时钟节流发送（不是满速狂发）

[接收端 Viewer]
读 broadcast.sdp
  → FFmpeg sdp demuxer（内部自动拉起 rtp/udp 协议）收包/去抖/重组
  → H.264 avcodec 解码（SPS/PPS 由 SDP 的 sprop-parameter-sets 自动配置，无感）
  → sws_scale：YUV420P → RGB
  → QImage → QLabel，30fps 定时刷新
  → 流中断 → 自动重建全新 demuxer 重连（~0.5s 自愈）
```

**模块与文件**：

| 模块 | 文件 | 职责 |
|---|---|---|
| 发送端引擎 | `broadcaster/src/video_engine.h/.cpp` | 采集→转换→编码→推流全流水线；start/stop；摄像头失败回退 test |
| 发送端界面 | `broadcaster/src/broadcaster_window.h/.cpp` | Qt 壳（开始/停止按钮 + 状态栏），工作线程跑引擎 |
| 发送端入口 | `broadcaster/src/main.cpp` | GUI / CLI（`-s` 源、`-t` 时长、`-f` 目标）双模式 |
| 接收端解码 | `viewer/src/h264_decoder.h/.cpp` | RAII 包装 avcodec 解码 + sws 转 RGB |
| 接收端收流 | `viewer/src/video_receiver.h/.cpp` | 读 SDP → demuxer 收流解码 → 供界面取帧；自动重连 |
| 接收端界面 | `viewer/src/viewer_window.h/.cpp` | QLabel 显示 + 状态栏，30fps 刷新 |
| 公共契约 | `common/params.h` | 两端共享参数（分辨率/帧率/码率/GOP/组播地址/端口） |

# 四、发送端逐层口径（本人主讲，要能逐行讲）

## 4.1 采集
- `VideoCapture` 打开 `/dev/video0`；打不开（无摄像头机器）自动切测试源，界面状态栏明确显示当前源（摄像头 / 测试画面），避免"看到测试画面以为摄像头坏了"。
- 摄像头重启占坑坑点：停止→立即再开始可能因设备未完全释放打开失败，处理：释放时显式置空对象 + 停止后短暂延时（约 200ms）。

## 4.2 像素转换（最容易翻车的环节）
- `sws_scale` 三大坑：① stride ≠ 宽度（linesize 有对齐补字节，读像素必须按 linesize 走行，否则画面斜撕）；② YUV420P 是 U 在前 V 在后，接反画面偏色不报错；③ 420 要求宽高为偶数（640×480 天然满足）。

## 4.3 编码（本项目最大知识块）
- 参数选择与理由：
  - **preset=ultrafast**：实时优先，软编 640×480 场景保证 30fps；
  - **Constrained Baseline**：去 B 帧等，兼容性最好（VLC/ffplay/老解码器通吃）；
  - **2Mbps / GOP=60**：GOP=60 ≈ 2 秒一个 I 帧（短 GOP），这是"断流自愈"的第一重保障；
  - **AV_CODEC_FLAG_GLOBAL_HEADER**：SPS/PPS 不在流内重复携带，只在 SDP 的 `sprop-parameter-sets` 里带外传 → 新接收端一打开 SDP 就具备完整参数集，无需等带内 I 帧（这也是 VLC 能直接播 SDP 的原因）。
- 正确做法备忘：`AVPacket` 必须 `av_packet_alloc()` 分配（栈上裸包传给 `avcodec_receive_packet` 会崩）；flush 编码器（发 `NULL` 帧）要把尾部缓冲排空。

## 4.4 推流与 SDP
- FFmpeg **rtp muxer** 一条路走通：RTP 拆包、时间戳（90000Hz）、FU-A 分包、RTP 头全部自动处理——这是"不自己造 RTP 轮子"的取舍理由。
- `GLOBAL_HEADER` 场景下必须等**第一个关键帧**写入后再生成 SDP，否则 SDP 里没有 `sprop-parameter-sets`，接收端永远无法开始解码（黑屏）。
- 发送节奏：不能把码流瞬间全发出去，必须按 30fps 的真实帧间隔节流，否则接收端缓冲区冲击大、画面堆积。
- UDP 无连接：发送端可任意启停；接收端程序绑定组播地址即收，不挑发送端 IP，跨机联调零配置。

## 4.5 Qt 线程模型（必背）
- 界面控件只能主线程操作；采集→编码→发送整条循环放工作线程；更新界面一律走信号槽；停止用原子标志 `request_stop` + `join` 收尾，保证线程安全退出、资源在引擎内部统一清理。

# 五、接收端口径

## 5.1 实现方式（为什么这么选）
- 读 SDP → FFmpeg **sdp demuxer**（自动拉起内部 rtp/udp 协议）：收包、按序号重组、去抖全交给标准实现，与 ffplay/VLC 行为一致。
- 需要显式放行 `protocol_whitelist`（Ubuntu FFmpeg 安全默认只有 `file,crypto,data`，不带 rtp/udp 会报 `Protocol 'rtp' not on whitelist`）。
- SDP 里 `sprop-parameter-sets` 经 demuxer 解析后自动填进解码器 `extradata`——接收端"无感拿到 SPS/PPS"；对比过去手写 RTP 的方案，这块恰恰是最容易错的。
- Qt 侧：H.264 解码器用 RAII 类管理资源；工作线程解码出新帧就覆盖"最新帧"（互斥锁保护），界面定时器每 ~33ms 取一次帧画到 QLabel。

## 5.2 自动重连（本项目最值得讲的设计）
- **现象**：发送端重启 = 全新 RTP 会话，RTP 时间戳从 0 重新数起；若接收端继续沿用旧 demuxer，其内部残留上一会话的时间基准，会把新包误判为"迟到包"丢弃（FFmpeg 刷 `RTP: dropping old packet received too late` / `bad cseq`），甚至收流中断。
- **方案**：收流中断（非用户主动停止）后，自动**销毁旧 demuxer、重建解码器、重新打开同一份 SDP**——新会话从头同步，发送端重启约 0.5s 内自动恢复画面，无需人工重启接收端；同时把 FFmpeg 日志压到 error 级，隐藏过渡期 warning 噪音。
- 一句话讲法："与其在旧会话状态上打补丁，不如让接收端把重启后的发送端当作新流重连一次，从根上避开新旧会话的时间基准冲突。"

# 六、面试高频追问预案

| 问题 | 答法要点（均有真实代码支撑） |
|---|---|
| 为什么编码 / 为什么 H.264 软编 | 裸数据 216Mbps 传不了；软编可控、学习价值高，硬编(VAAPI)留作优化项 |
| 为什么 GLOBAL_HEADER + SDP 带外传参数 | SPS/PPS 只在流内靠 I 帧附近出现，中途加入的接收端等不起；放 SDP 带外传，打开即具备完整参数集 |
| 为什么用 rtp muxer/demuxer 而非手写 socket | RTP 拆包/序号重组/去抖/FU-A 是易错细节；FFmpeg 实现与 ffplay/VLC 天然互通，测试即行业标准 |
| 为什么组播 | 单向广播天然适合 UDP；发送端只发一份，接收端数量不增加发送负载，免维护接收端列表 |
| 断流恢复怎么做 | 两重：① 短 GOP（2s 一 I 帧）→ 丢包/中途加入最多等 2s 自愈，省 I 帧请求信令；② 接收端中断后重建会话重连 |
| 发端重启为什么接收端会丢画面 | 新会话时间戳从 0 重数，旧 demuxer 残留状态判其为"迟到包"→ 所以要做"重建 demuxer"而非沿用 |
| 发送节奏为什么按帧节流 | 防码流瞬间灌入、接收端缓冲冲击；30fps 真实时钟 |
| Qt 线程安全怎么做的 | 控件只主线程、工作线程 + 信号槽、原子标志 + join 优雅停止 |
| SDP 是什么、为什么需要 | 会话描述：告诉接收端"流在哪个组播地址端口、什么编码、参数集在哪"，一个文件就能开流 |
| 踩过什么坑 | extern "C" 包裹 FFmpeg 头；`av_packet_alloc` 必用；pts/dts 需从编码器基准换算到容器基准（否则 mp4 时长错误）；协议白名单要放行 rtp/udp；VLC 系统版(snap vs apt) SDP 解析差异 |
| 参数怎么保证两端一致 | 不各写一份，集中 `common/params.h` 契约头，改一处两端生效 |

# 七、真实踩坑记录（面试素材，均为本次开发实际发生）

1. FFmpeg 头文件不自带 `extern "C"` 保护 → 链接报 mangled 符号，需整体包裹；
2. 栈上裸 `AVPacket` 传入 `avcodec_receive_packet` → `free(): invalid pointer` 崩溃；
3. 写 mp4 时长≈0 错误 → pts/dts 未从编码器 time_base(1/30) 换算到容器 time_base，需 `av_rescale_q_rnd`；
4. `Protocol 'rtp' not on whitelist` → Ubuntu FFmpeg 协议白名单安全限制，需 `protocol_whitelist` 放行；
5. VLC 版本差异：apt 版 SDP 解析有 bug 黑屏，snap 版正常 → 验证工具版本要固定；
6. 发送端停止→重启，接收端刷 `dropping old packet / bad cseq` → 时间戳会话冲突，用"重建 demuxer 自动重连"根治；
7. 摄像头停止后快速重开失败 → 显式释放 + 停止后延时；
8. "接收端没开推流也有画面"的误会 → viewer 不生成任何画面，收到的每一帧都来自 RTP 流（排查先确认有无残留发送端进程）。
